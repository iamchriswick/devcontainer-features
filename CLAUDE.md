# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working rules

- Act only on what the user, the spec, a ticket, a skill or a hook explicitly instructs. Nothing else.
- You make no decisions and hold no opinions on this project. Give an opinion only when the user asks for one.
- If anything is unclear, ask before acting. Never guess or interpret intent.
- Ask every question with AskUserQuestion, after stating the reason in chat. Don't ask whether to ask.
- Never state an assumption as a fact. Verify it, or say plainly that it is unverified.
- A question from the user is a question: answer it, don't act on it.
- Answer exactly what the user wrote. If you don't understand a question or instruction, ask with AskUserQuestion; never substitute your own interpretation.
- No unsolicited suggestions, options, offers or `Next:` lines unless a skill asks for them.
- If you broke a rule, name the rule. No justifications, no explanations, no arguing.
- Answer in full, direct sentences. No one-word or dash replies.
- Don't touch PRs, tickets, branches or GitHub unless the user says so.
- Undo your own unapproved changes yourself; don't ask the user how to clean them up. Confirm destructive git actions (force-push) with AskUserQuestion.
- `.claude/` and `CLAUDE.md` changes go on a branch `ai/claude-<description>` cut from `feat/claude-code-persistent`: push it, merge it back into the local `feat/claude-code-persistent`, then delete the local `ai/claude-*` branch.

## Gotchas

- `.claude` is in `.gitignore`. Stage changes to tracked files there with `git add -u`, never `git add -f`.
- Never test `claude-code-persistent` in this repo's own dev container: it already installs Claude Code, so tests pass falsely.
- A scenario that needs Node.js (e.g. with `ghcr.io/anthropics/devcontainer-features/claude-code`) adds `ghcr.io/devcontainers/features/node:2`.
- Cloud sessions: `gh issue`, `gh pr` and `gh label` go through GraphQL and get HTTP 403; use `gh api` (REST).

## What this repo is

A collection of [Dev Container Features](https://containers.dev/implementors/features/), published to GHCR as `ghcr.io/iamchriswick/devcontainers/features/<id>`. It is the `features` submodule of `iamchriswick/devcontainers`: pushes to `main` dispatch `submodule-updated` to that repo (`notify-main.yml`).

- `src/<id>/`: one folder per Feature. `devcontainer-feature.json` (its `id` must equal the folder name) and `install.sh`, which runs as root at image build. Other files in the folder ship with the Feature.
- `src/<id>/README.md` is generated by the release workflow from `devcontainer-feature.json` plus `NOTES.md`. Edit `NOTES.md`, not the README.
- `test/<id>/`: `scenarios.json` (each key is a scenario, each value a `devcontainer.json`) plus one script per scenario, named after it. `test.sh` is the auto-generated test. `test/_global/` holds scenarios that combine several Features.
- Specs and tickets live in GitHub issues; `.specs/` is local only (in `.git/info/exclude`).

## Commands

Tests need a running Docker daemon and the devcontainer CLI (`npm install -g @devcontainers/cli`). Run from the repo root.

```bash
# All scenarios of one Feature
devcontainer features test -f <id> --skip-autogenerated .

# One scenario
devcontainer features test -f <id> --skip-autogenerated --filter <scenario> .

# Auto-generated test against a base image
devcontainer features test --skip-scenarios -f <id> -i mcr.microsoft.com/devcontainers/base:ubuntu .

# Global scenarios
devcontainer features test --global-scenarios-only .
```

## CI and release

- `test.yaml` (push to `main`, PRs): the Feature matrix lists only `lla`. Other Features' tests do not run in CI.
- `validate.yml`: validates every `devcontainer-feature.json` with `devcontainers/action` (`validate-only`).
- `release.yaml`: manual (`workflow_dispatch`, `main` only). Publishes the Features, regenerates their READMEs in a PR, and dispatches to `iamchriswick/devcontainers`.
- Each Feature is versioned by `version` in its `devcontainer-feature.json` (semver).

## Feature notes

### `lla`

`install.sh` uses nanolayer to run the `ghcr.io/devcontainers-extra/features/gh-release` Feature for `chaqchase/lla`. Resolving `latest` calls the GitHub API unauthenticated, so CI jobs can fail with `HTTP Error 403: rate limit exceeded`.

### `claude-code-persistent`

Spec: GitHub issue #2; its tickets are sub-issues. It persists Claude Code data in the named volume `claude-code-persistent`, mounted at `/mnt/devcontainers/features/claude-code-persistent` (`conf/`, `tmp/`). Debian-based images only. The work is split across build time and lifecycle hooks:

- `install.sh` (build, root): creates the mount point, stages `util.sh`, `onCreate.sh` and `updateContent.sh` in `/usr/local/share/devcontainers/features/claude-code-persistent/hooks`, and writes the build-time option values into the staged `updateContent.sh` as its defaults.
- `onCreate.sh` (`onCreateCommand`): installs Claude Code as the remote user with the native installer, unless `claude` is already on the remote user's PATH.
- `updateContent.sh` (`updateContentCommand`): backs up existing data as `.old`, links `~/.claude`, `~/.claude.json` and `~/.claude/.credentials.json` into `conf/`, and writes `/etc/profile.d/claude-code-persistent-*.sh` exporting `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_TMPDIR`.
- Lifecycle hooks run as the remote user from the workspace folder, so they load `util.sh` relative to `$0`.
- The `preinstalled` scenario installs the Node Feature first: the anthropics `claude-code` Feature needs Node.js and npm, and `base:debian` has neither.
